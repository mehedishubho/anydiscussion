<objective>
Close UAT gaps 3 and 4 (Phase 5 UAT tests 4 and 5): make the redirects-table check actually fire on the self-hosted runtime, and make the SEO settings page discoverable from the dashboard sidebar.

Gap 4 (blocker): src/app/not-found.tsx RedirectChecker reads the `x-invoke-path` request header — an internal VERCEL-injected header that never exists on self-hosted Next.js (this project deploys via Coolify, no Vercel). incomingPath is always null, the DB lookup never runs, and a populated redirects row (verified present in dev DB: id 1, /old -> /new, 301) is ignored — visiting /old returns 404. Fix: middleware.ts explicitly sets the incoming path as a request header on every matched request (NextResponse.next({ request: { headers } }) — documented Next.js middleware request-header override) and the matcher is extended to public paths, so the app-side headers() read gets the real pathname. Chosen over a [...catchAll] route because the header mechanism is one-line, keeps 404 rendering semantics unchanged, and requires no route-tree surgery.

Gap 3 (major): src/layout/AppSidebar.tsx Settings submenu lists Storage, Backup, Newsletter — the /dashboard/settings/seo page (shipped and working per UAT test 4) was never linked, forcing URL navigation. Fix: add the SEO subItem.

Output: Fixed middleware.ts + not-found.tsx + AppSidebar.tsx; live-verified 308/307/404 behavior.
