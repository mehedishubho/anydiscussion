    **Title:** ADR 0001: Single-Instance ISR Scaling Cliff
    **Status:** Accepted (v1; revisit before adding a second Coolify replica)
    **Context:** Describe the problem — Next.js ISR (`revalidatePath`/`revalidateTag` + `cacheComponents:true` + `'use cache'` directives) relies on an in-memory cache by default. On a single Coolify instance this works: the cache lives in the running Node process, `revalidatePath` flushes it, the next request regenerates the page. When a second Coolify replica is added (for horizontal scaling or zero-downtime deploys), each replica has its OWN in-memory cache — a publish hitting replica A flushes A's cache but replica B continues serving stale content until its own TTL expires or its own revalidation fires. This is the "ISR scaling cliff." Reference the cacheTag-wired routes from Phase 3/5/6 (post pages, sitemap, RSS, taxonomy archives) and the publish→visible loop (Plan 07-03) as the user-visible symptom.
    **Decision:** For v1, run a single Coolify instance (D-32 — no staging, single-environment production). This sidesteps the cliff entirely. Document the trade-off: a single-instance outage takes down the site (acceptable for a small team per D-32; restart policy `unless-stopped` recovers from container crashes).
    **Consequences:**
    - Positive: ISR works correctly out of the box; no shared-cache infrastructure to operate; publish→visible latency is sub-30s on the single instance.
    - Negative: No horizontal scaling in v1; a deploy briefly takes the site down (Coolify default deploy strategy).
    - v2 path: Before adding a second Coolify replica, implement a shared Redis-backed `cacheHandler` (singular form — NOT the deprecated `incrementalCacheHandlerPath` name). Document the interface: `get`, `set`, `revalidateTag`, `resetRequestCache`. Reference the existing src/lib/redis/index.ts singleton (Plan 07-02) as the connection primitive the cacheHandler would use. Cross-reference SCALE-01 (v2 requirement).
    **References:**
    - Next.js `cacheHandler` documentation (stable since Next 14.1; image-cache support added Next 16.2.0)
    - Project ROADMAP v2 → SCALE-01
    - Plan 07-02 (Redis singleton primitive)
    - Plan 07-03 (publish→visible loop that the cacheHandler would coordinate across replicas)
