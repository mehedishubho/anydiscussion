## Phase Goal

**As a** founder, **I want to** rate-limit all auth endpoints and the Contact form against a self-hosted Redis, **so that** brute-force and enumeration attacks are blunted without introducing any cloud dependency.

<objective>
Rate-limiting slice (PERF-04, honors D-01 literally): the canonical auth-endpoint path uses Better Auth's built-in `rateLimit.customRules` + `customStorage` backed by ioredis; the Contact form migrates from in-memory to `@upstash/ratelimit` + ioredis via a small adapter. Redis is added to docker-compose for dev parity.

Purpose: D-01 locks `@upstash/ratelimit` + ioredis against self-hosted Redis. RESEARCH.md finding #1 reconciles this with the canonical auth path: Better Auth's built-in `rateLimit` is the integration point for auth endpoints (NOT middleware, NOT a Server-Action wrapper); `@upstash/ratelimit` is repurposed for the Contact form. This honors D-01 literally while keeping the auth path canonical. The `@upstash/ratelimit` package carries a SUS metadata flag (no repository field in its package.json), so the install is gated by `checkpoint:human-verify` per the phase directives.

Output: Redis singleton + docker-compose Redis + Better Auth rateLimit config + ioredis-adapter + migrated Contact limiter + integration test + .env.example REDIS_URL.
</objective>
