Fix the two Phase 05 UAT R1 blockers found in the post-05-08 live re-test. Both are fully root-caused — implement the fixes below, do NOT re-derive.

**Bug 1 — edit-page client crash `TypeError: Cannot read properties of null (reading 'can')`** (upstream ueberdosis/tiptap#7849). `Editor.destroy()` nulls the internal commandManager (verified in installed @tiptap/core dist index.js:6168) but leaves the editor instance non-null; `can()` reads `this.commandManager.can()` (dist:5771), producing the exact error. In dev (React StrictMode), `useEditorState` re-invokes the UNMEMOIZED selector with the destroyed editor during the mount→remount cycle. The guard at src/components/editor/toolbar/Toolbar.tsx:109 only checks null — a destroyed editor passes it — so `e.can().undo()` at line 131 throws and bubbles to src/app/error.tsx. The upstream fix (PR #8015) is NOT in installed @tiptap/react 3.27.1, so an app-level `isDestroyed` guard is the correct immediate fix (same workaround Tiptap maintainers and Mantine recommend).

**Bug 2 — publish fails Zod "Invalid url" when the feature image comes from the media library.** MediaPicker.resolvePublicUrl (src/components/dashboard/media/MediaPicker.tsx:56-61) emits ROOT-RELATIVE URLs `/api/media/<providerKey>` — the correct portable convention (same-origin next/image optimization works; the user's log shows `GET /api/media/...?w=640&q=75 200`, so rendering already works). But src/actions/posts-schema.ts:38 `featureImage: z.string().url().optional().or(z.literal(""))` requires ABSOLUTE URLs → Zod rejects → publish toast shows "Invalid url". Same pattern: posts-schema.ts:50 (ogImage), src/lib/seo/validation.ts:61 (ogImage), src/actions/seo-settings-schema.ts:29 (defaultOgImage — image-typed field, same rejection awaits a local media URL there). canonical/canonicalUrl/base-URL fields MUST stay strictly absolute (SEO contract).
