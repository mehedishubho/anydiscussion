# CONTEXT — Quick Task 260824-3l2: Functional frontend newsletter with dashboard configuration

**Created:** 2026-08-24 (discuss phase, `--full` pipeline)
**User request (verbatim):** "make function for front end newslatter so it can be functional and can be configure it from dashboard , so discuss,research, plan then excutete it"

## Summary

The footer Newsletter column (SiteFooter col 4) is currently inert visuals — an `<input>` + `type="button"` with no form element and no Server Action (260823-6je decision 2 deliberately deferred backend wiring to this task). Make it functional: real subscribe flow storing subscribers in Postgres, plus dashboard configuration and subscriber management.

## Decisions

### D-01 — Single opt-in — subscriber saved as active immediately

No confirmation-email round-trip. The subscribe Server Action validates the email and inserts with `status = 'active'` on first subscribe. Re-subscribing an existing active email is an idempotent no-op success (never an error); re-subscribing a previously unsubscribed email flips it back to active.

**Why:** Real email delivery is deferred until `RESEND_API_KEY` + DNS deliverability are configured (project decisions D-03/D-04, Phase 2 UAT debt). Double opt-in now would strand every subscriber in "pending" with no email able to reach them. Single opt-in works today with zero email dependency and can be upgraded to double opt-in later by adding a pending status + confirmation flow on top of the same table.

### D-02 — Dashboard configuration — enable toggle plus the three text strings

Settings keys (key-value `settings` table, same pattern as `footer.social_*`):

- `newsletter.enabled` — `"true"`/`"false"` (default `"true"`). When `"false"`, the footer renders NO newsletter column at all (not a disabled form).
- `newsletter.heading` — column heading (default `"Newsletter"`)
- `newsletter.description` — the blurb under the heading (default `"Subscribe for the latest posts delivered straight to your inbox."`)
- `newsletter.success_message` — inline confirmation after subscribing (default `"Thanks for subscribing!"`)

Dashboard UI lives in Settings as a Newsletter section/page following the existing settings-page patterns (admin-only save action; saving revalidates the footer cache via the existing `seo-settings` tag so the footer picks up new text/visibility without a rebuild).

**Why:** Matches the established settings-key + cached-footer architecture — `SiteFooter` is a `'use cache'` boundary already tagged `seo-settings`, so toggling/text changes refresh it through the existing revalidation path with zero new cache machinery.

### D-03 — Subscriber management — admin-gated list plus delete plus CSV export

A dashboard page (admin role only — `requireRole` first in every action, per the never-optional permission rule):

- Table of subscribers: email, status, subscribed-at timestamp, paginated
- Delete subscriber (Server Action, confirm-in-UI)
- Export CSV (download of email,status,subscribed_at — admin-gated route or action)

No bulk actions, no editing, no create — this is a list hygiene surface, not a CRUD editor.

**Why:** Standard minimum for a usable list. Editing subscribers by hand invites typos into a field the subscriber owns; creation is what the public form does.

### D-04 — Unsubscribe is schema-ready but no public route in this task

The subscribers table carries a unique token column so a future `/newsletter/unsubscribe?token=…` route can flip status to `unsubscribed` without email delivery. This task does NOT build the public unsubscribe page (it is unreachable until emails actually send — nothing carries the link).

**Why:** Adding the token column now costs one migration column and avoids a second migration the day email goes live; building an unreachable page now costs UI nobody can reach.

### D-05 — Spam protection via honeypot plus simple rate limit

The subscribe form includes a hidden honeypot field (any value = silent success, no insert) and the Server Action rate-limits by IP (same approach/pattern as existing auth rate limiting where reusable; otherwise an in-memory window per process — acceptable for a single-instance VPS deployment).

**Why:** The form is public and unauthenticated. Honeypot blocks naive bots at zero UX cost; per-IP limiting blunts scripted floods. No CAPTCHA — paid/no-API constraint and overkill for v1.

### D-06 — Form mechanics follow the public-site minimal-JS rule

Server Action (`src/actions/newsletter.ts`) as the only mutation path (project convention). The footer newsletter column becomes a small client component (form + useActionState for pending/success/error) rendered inside the cached footer — the cache boundary stays intact; only the island is interactive. Non-JS fallback degrades to the current inert visuals (progressive enhancement is nice-to-have, not a gate).

**Why:** Keeps the footer as a cache boundary while making the form interactive; a client island is the established Next.js 16 pattern for form state without pulling dashboard-grade JS onto the public site.
